# Bhutan Vegetable Market Prices - Reproducible Data Pipeline

DAM405 · Machine Learning Operations · Programming Assignment 1

A small, version-controlled, automatically-tested pipeline that ingests raw
Bhutanese vegetable-market data from two source formats, cleans and enriches
it, validates it against a data-quality gate, and lands it in a queryable
SQLite store (plus Parquet for downstream ML tooling).

## What it does

```
data/raw/market_prices.csv  ─┐
                              ├─▶ ingest ─▶ transform ─▶ quality gate ─▶ store
data/raw/dzongkhag_metadata.json ─┘                         │
                                                    (stops the pipeline
                                                     if validation fails)
```

- **Ingestion** (`src/ingest.py`) — reads a CSV of daily market-price
  records and a JSON file of dzongkhag reference metadata. The CSV loader
  also accepts an optional live `--source-url`, with automatic fallback to
  the cached local file if the live source is unreachable.
- **Transformation** (`src/transform.py`) — types and cleans the data
  (dates, numeric coercion, text normalisation, de-duplication, dropping
  invalid rows), joins it against the dzongkhag metadata, and adds three
  derived features: `revenue_nu`, a per-commodity `price_zscore` /
  `is_price_outlier` flag, and `day_of_week`.
- **Quality gate** (`src/quality.py`) — six assertion-based checks (schema,
  completeness, value ranges, categorical membership, uniqueness,
  referential integrity). If any check fails, the pipeline raises
  `DataQualityError` and **stops before writing anything to the store**.
- **Storage** (`src/storage.py`) — writes the curated batch to a SQLite
  table (`curated_market_prices`) and a Parquet file.

## Setup

```bash
git clone <this-repo-url>
cd mlops-pipeline
python -m venv .venv && source .venv/bin/activate   # optional but recommended
pip install -r requirements.txt
```

## Running the pipeline (single documented command)

```bash
make all
```

This installs dependencies, (re)generates the raw source files, runs the
pipeline end to end, and runs the test suite. Equivalently, step by step:

```bash
python -m src.generate_raw_data   # only needed once, or to reseed the data
python -m src.pipeline            # run the pipeline
pytest -v                         # run the tests
```

To point the pipeline at a live CSV endpoint instead of the cached file:

```bash
python -m src.pipeline --source-url https://example.com/market_prices.csv
```

## Querying the curated store

```bash
sqlite3 data/processed/market_prices.db \
  "SELECT dzongkhag, ROUND(AVG(price_nu_per_kg),2) AS avg_price FROM curated_market_prices GROUP BY dzongkhag;"
```

or from Python:

```python
from src.storage import query
query("SELECT * FROM curated_market_prices LIMIT 10")
```

## About the dataset

The raw CSV/JSON pair is synthetically generated by
`src/generate_raw_data.py` using a fixed random seed, so the whole project
is reproducible offline without depending on a third-party endpoint staying
online. The generator deliberately injects realistic "dirty data" (missing
values, negative prices, inconsistent text formatting, duplicate rows) so
the cleaning logic and the quality gate have genuine work to do. See the
accompanying report for the rationale and for how this maps onto the data
engineering lifecycle.

## Data-quality gate — what it rejects

| Check | Rejects when… |
|---|---|
| Schema | a required column is missing |
| Completeness | `date`, `dzongkhag`, `commodity`, `price_nu_per_kg` or `quantity_kg` is null |
| Value range | `price_nu_per_kg` or `quantity_kg` is ≤ 0 |
| Categorical membership | `dzongkhag` is not one of Bhutan's 15 recognised dzongkhags in the reference data |
| Uniqueness | fully-duplicated rows remain after cleaning |
| Referential integrity | a row failed to join against the dzongkhag metadata (null `region`) |

These are implemented as plain pandas assertions rather than Great
Expectations to keep the dependency footprint small; each check maps 1:1
onto a GE `Expectation` (e.g. `expect_column_values_to_not_be_null`,
`expect_column_values_to_be_in_set`) and could be swapped in without
changing the pipeline's interface.

## CI

`.github/workflows/ci.yml` runs on every push and pull request: it installs
dependencies, lints with flake8, runs the test suite with pytest, and runs
the pipeline end-to-end as a smoke test.

## Tests

`tests/test_transform.py` and `tests/test_quality.py` cover the
transformation logic (cleaning, joining, feature engineering) and every
branch of the quality gate, including that a valid batch passes and each
category of invalid batch is correctly rejected.

## Limitations & possible improvements

- The dataset is synthetic; a production version would point
  `--source-url` at a real NSB/market-information-system export.
- Great Expectations (or `pandera`) would give richer validation reports
  and HTML data-docs than the current hand-rolled checks.
- No orchestration/scheduling layer (Airflow/Prefect) — the pipeline runs
  once per invocation; a production deployment would schedule it daily.
- No data versioning (DVC/lakeFS) for the raw/curated datasets themselves.
